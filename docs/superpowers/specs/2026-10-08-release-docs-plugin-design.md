# release-docs 獨立插件設計

日期：2026-10-08

## 目標與範圍

建立獨立的 `release-docs` 插件，讓過版執行者能依 Git 實際異動取得結構 SQL、資料 SQL、appsettings 異動與上線指引。Redmine 是選用的需求與單號來源；未連接時仍能產出全部文件。

第一版在獨立 GitHub 專案 `zokmi/release-docs-plugin` 的根目錄建立可打包插件，使用自己的 manifest、README、skills、範本與驗證資源。現有 Redmine 插件與 Claude Code 已安裝技能保持原狀。建立遠端 repository、發布與安裝不在本次範圍。

## 架構

採用一個統一入口技能 `release-docs`，負責確認範圍、蒐集 Git 證據、閱讀腳本與程式、分類異動、填寫四份範本、確認相依順序與交付。插件不需要 MCP server，也不綁定資料庫連線或 Redmine 憑證。

沿用目前套件的 Claude Code 與 Codex 插件封裝方式，提供各自的 manifest 與各工具實際支援的 marketplace 入口。安裝、更新及移除一律透過插件管理器，不提供複製 skills 或獨立腳本作為產品安裝方式。發布來源尚未指定時先驗證本地 marketplace 的插件安裝流程，不虛構遠端網址；實際安裝與發布仍需使用者要求。SQL 判讀規則取自個人 `sql-release-signoff` 技能；Git 與設定異動判讀參考現有 `release-change-items`，改成此次獨立插件的文件流程。

## 輸入與證據

- 讀取目標專案的 AGENTS.md、CLAUDE.md 與資料庫／部署慣例。
- 以 `git rev-parse --show-toplevel` 定位目標 Git 根目錄。
- 支援使用者指定的基準與目標 revision、版本範圍或明確 commit 清單。記錄實際使用的 diff 模式與解析後 commit；基準不明時詢問，不預設 main。
- 同時盤點 staged、unstaged、untracked 的相關異動，與指定已提交範圍分開記錄，標示是否納入此次部署；不能把工作區內容冒充指定版本內容。
- 完整閱讀 SQL 與 migration；對照 ORM 實體、內嵌 SQL、設定鍵的程式使用處與部署流程，找出缺少腳本或設定的缺口。
- 沒有單號的異動仍納入盤點，不要求每次過版必須有 Redmine 單號。版本或單號不明時先確認文件識別名稱。
- Redmine 工具可用且有指定單號時，選用讀取需求資訊；不可用時依 Git 產出，明示未取得的資訊。

## 輸出契約

固定輸出至 `<Git 根目錄>/docs/<YYYY-MM-DD>_<版本或單號>/`，日期使用使用者當地的產出日期，識別名稱需移除路徑分隔符與不合法字元，確保結果在 docs 內。

| 文件 | 必備內容 |
| --- | --- |
| `01_結構SQL.md` | 表、欄位、索引、約束、預存程序等異動；來源腳本與 revision、執行單位、相依、執行前檢查、執行後驗證及預期結果 |
| `02_資料SQL.md` | 種子資料、修正、回填、遷移與刪除；資料條件、影響範圍、重跑限制、驗證及失敗處理 |
| `03_appsettings異動.md` | 設定檔路徑、完整設定鍵、增加／修改／移除、舊值與新值或正式環境待填值、設定來源優先順序、套用方式、重啟與驗證 |
| `04_上線指引.md` | 版本與單號、Git 範圍、四份文件連結、前置條件與備份、SQL／設定／程式部署的交錯順序、驗證、停止條件、失敗處理、回復限制、UAT 與正式執行／簽核紀錄 |

四份文件皆須產出；沒有異動的類別明寫「無」。每項結論引用來源；無法證實的內容寫「待確認（原因）」，不可將未查證寫成無。

第一版輸出 Markdown 文件與現有 SQL／migration 的引用，不自動新增、拆分或修改可執行部署 SQL。混合 DDL/DML 腳本可在兩份文件分別說明，但在上線指引只列一個完整執行單位，保留交易、批次及原有相依，避免重複執行。migration 工具同樣保留原有執行單位。

## 上線規則

- 依實際相依決定順序，不依檔名日期直接排序；涵蓋 SQL、設定、程式部署及必要的人工作業。
- 記錄交易、可否重跑、部分成功、靜默跳過、警告、鎖表與資料覆蓋風險。沒有證據不臆測時間或筆數。
- 驗證查詢需符合專案資料庫方言，列出可查證的預期值或條件；不執行正式資料庫操作。
- appsettings 是主要設定來源，亦納入同次異動的環境變數與其他實際部署設定；不猜測正式環境使用開發設定值。
- 密碼、token、API key 與連線憑證遮罩，正式環境值以待填及既有安全設定來源指示呈現；文件與蒐集結果不得洩漏原值。
- 原文件沒有簽名或執行紀錄時可就地更新並留異動記錄；已有紀錄時另建 `_v2`、`_v3` 等資料夾，引用取代原因，保留舊文件。
- 非 Git 目錄時要求提供目標專案；不任選輸出位置。無權限讀取或证據缺漏時明示限制。

## 必要審查關卡

產生四份文件後，必須進行另一輪審查，重新讀取 Git 範圍、原始腳本、設定差異及四份成品，不能只對照範本或沿用產出時的摘要。第一版將審查定義為獨立步驟；不要求特定模型、額外付費服務或可用的 subagent。

審查結果記錄在同資料夾的 `05_版更審查報告.md`，作為四份版更文件之外的品質紀錄，包含審查時間、涵蓋的 revision 與工作區內容、受審文件識別、檢查項目、問題等級、來源證據、修正與複審結果。

必檢項目：

1. 完整性：指定範圍的結構、資料、設定異動是否漏列，未提交內容是否清楚區分，ORM 異動是否缺少部署腳本。
2. 正確性：每項說明能否對應來源；SQL 方言、資料條件、設定鍵、預期值與實際內容是否一致。
3. 相依與執行：順序是否包含 SQL／設定／程式的依賴，混合腳本是否重複列為可執行步驟，是否破壞交易或批次。
4. 可驗證與可恢復：檢查項能否操作，失敗時是否知道停止位置、重跑限制、部分提交與回復條件；禁止猜測安全回滾。
5. 文件安全與一致性：敏感值遮罩、連結可解析、範圍與執行順序一致、原有簽核紀錄保留。

審查狀態為「通過」「待確認」「未通過」：漏列必跑異動、錯誤執行順序、敏感值外洩或錯誤部署／回復指令屬阻擋問題，判定未通過。正式設定值、資料量或其他必要證據待補時判定待確認。只有必檢項完成且沒有未解決問題才能通過。文件審查通過不代表 SQL 已測試、正式環境已驗證或人工簽核完成。

可由來源證據直接修正的問題先修正，再重新審查受影響的項目與四份文件的一致性；最多三輪，仍未解決時留下明確問題與所需資訊，不無限循環或降低通過標準。後續任何成品或部署來源異動均使舊審查失效，必須重新審查。上線指引連結審查報告並標示狀態，交付摘要同步呈現狀態與阻擋事項。

## 第一版驗收

1. 插件可獨立封裝，不依賴 Redmine MCP；兩種 manifest 的名稱與版本一致，技能及範本引用完整。
2. 以臨時 Git fixture 驗證：結構 SQL、資料 SQL、混合腳本、設定鍵新增修改刪除、未提交檔、無異動與不明基準。
3. 驗證混合腳本只執行一次、輸出留在 Git 根目錄 docs、敏感設定不進文件、已簽核文件保留。
4. 驗證所有文件有來源與共同範圍、上線指引的連結及執行順序一致；缺漏明示待確認。
5. 檢查封裝與技能結構，提供可在 Claude Code／Codex 使用的範例。尚未實際安裝的環境不宣稱安裝成功。
6. 以漏列異動、重複執行混合 SQL、錯誤設定鍵與敏感值等刻意缺陷驗證審查能指出證據並阻擋通過；確認修正後複審、待確認狀態及審查失效規則。
